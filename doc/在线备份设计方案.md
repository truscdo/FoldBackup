# 在线备份设计方案

本文定义在线快照中 Region LRH blob 和普通文件 blob 的去重方式。归档 LRHD 使用独立流程，不在本文范围内。

## 1. 基本模型

- 每个快照保存完整 manifest：相对路径、条目元数据和 blob 引用。
- 运行时保存一条最新的 manifest，通过文件路径匹配元数据，实现文件变化快速检测。
- blob 按内容哈希全局复用；多个路径和多个快照可以引用同一个 blob。

```text
快照 manifest
└─ 相对路径
   ├─ 条目元数据
   └─ blob 引用
```

## 2. 元数据与哈希

### 2.1 源文件元数据

源文件元数据用于上一快照的快速对比，普通文件记录文件大小、修改时间和 `fileKey`；这些属性不可用时按实际文件系统能力处理。

Region 的元数据覆盖一个完整 Region 单元：

- `.mca` 文件的大小、修改时间和 `fileKey`；
- 所有关联 `.mcc` 文件的相对文件名、大小、修改时间和 `fileKey`；

运行时建立以下路径索引：

```text
latestMetadata
└─ relativePath → Metadata + BlobRef
```

### 2.2 内容哈希

| 名称 | 对象 | 定义 | 索引和用途 |
| --- | --- | --- | --- |
| `contentHash` | Region | XXH3-128：按 Region 网格顺序拼接解压后的区块 NBT，再拼接 1024 项大端 i32 区块长度表；不包含时间戳 | `contentHash → LRH BlobRef`，作为 LRH 的内容身份 |
| `sourceHash` | 普通文件 | XXH3-128：文件原始字节 | `sourceHash → Zstd BlobRef`，作为普通文件的内容身份 |

两个哈希都不包含文件路径，因此相同内容可以跨路径复用。它们是高速的非密码学哈希，适合常规去重，不提供抗恶意碰撞的完整性认证。

Region 的 `contentHash` 不包含时间戳，因此相同区块内容但时间戳不同的 Region 会复用同一个 LRH；复用时保留已有 LRH 中的时间戳表。

## 3. 去重流程

扫描开始时加载最新快照的 manifest 并建立 `latestMetadata`。每个当前文件只与该索引中相同路径的条目进行快速对比。

```text
扫描当前路径
└─ 查询 latestMetadata[path]
   ├─ 命中、源元数据未变化且 Blob 存在
   │  └─ 直接复用已有 Blob
   └─ 未命中、源元数据变化或 Blob 不存在
      ├─ Region
      │  └─ 计算 contentHash
      │     ├─ LRH 索引命中: 复用 LRH
      │     └─ 未命中: 压缩并写入 LRH
      └─ 普通文件
         └─ 计算 sourceHash
            ├─ Zstd 索引命中: 复用 Zstd blob
            └─ 未命中: 压缩并写入 Zstd blob
```

### 3.1 Region

关联 `.mcc` 不作为独立文件处理，而是 Region 的一部分。

1. 按相对路径查找最新快照的 Region 元数据。
2. 元数据未变化且 LRH 存在时，直接复制上一条 RegionEntry。
3. 否则流式读取 `.mca` 和 `.mcc`，解压区块并计算 `contentHash`。
4. 查询全局 LRH 索引；命中时引用已有 LRH。
5. 未命中时再次流式读取并写入 LRH，提交新的 `contentHash` 对应 blob。

LRH 不携带源文件路径和 Region 坐标，因此同一个 LRH 可以被不同路径引用。

需要注意的是Region可能存在元数据时间戳改变而contentHash不变的情况，这种情况应该复用LRH的同时更新快照的时间戳，以避免下次快速对比重新计算contentHash。

### 3.2 普通文件

1. 按相对路径查找最新快照的文件元数据。
2. 元数据未变化且 Zstd blob 存在时，直接复用上一条 FileEntry。
3. 否则流式读取文件并计算 `sourceHash`。
4. 查询全局 Zstd 索引；命中时复用已有 blob，即使路径不同。
5. 未命中时边读取边压缩，并提交新的 `sourceHash` 对应 blob。

## 4. 快照提交与垃圾回收

扫描完成后生成新的完整 manifest，并将其与条目元数据一次性提交到索引。

- 新 blob 在 manifest 提交前写入仓库。
- 索引提交后，所有存活快照的条目共同决定 blob 引用集合。
- 删除快照只删除其引用；不再被任何存活快照引用的 metadata 和 blob 由 GC 回收。
- blob 是否可作为去重候选取决于它是否仍被存活快照或索引保留。
- 写入或提交中途失败时，可能产生暂时无引用的 blob，由后续 GC 回收。

## 5. 一致性边界

- 元数据未变化时信任文件内容未变化，以避免重复读取大型文件。
- 备份前应保存世界并暂停自动保存，降低扫描期间源文件变化的机会。
- 如果源文件在读取过程中变化，必须以实际读取到的内容计算哈希并提交，同时记录源文件变化警告。
- 哈希碰撞概率很低，但 XXH3 不是密码学哈希；需要抗恶意篡改时应增加独立的完整性校验。
- 需要检测“内容变化但元数据被恢复”的情况时，应提供强制完整扫描或定期校验模式。
- 当前扫描会跳过零字节文件、过滤规则排除的文件和独立的 `.mcc` 文件；`.mcc` 由所属 Region 处理。
